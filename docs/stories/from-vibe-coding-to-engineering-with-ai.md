# 从 Vibe Coding 到 Engineering with AI：Gouno UI 是怎么被“逼”出来的

> 作者：阿笨  
> 日期：2026-09-10

![从混乱原型到设计系统](./assets/gouno-ui-vibe-to-engineering/01-cover.webp)

最近一段时间，我一直在折腾一个叫 **Gouno UI** 的项目。

如果只看现在，它已经越来越像一个正常的工程级 UI System：有 Core、Theme、Patterns、Gouno 等明确层级，有公共 API 规范，有设计语言，有 Showcase，有真实产品页面的验证，也有针对抽象是否应该进入公共层的准入规则。

但它一开始完全不是这样。

准确一点说，Gouno UI 并不是我一开始就规划好、然后按图施工做出来的。它是从 Gouno Blog 一路开发、失控、重构、再失控、再重新认识问题的过程中，一层一层“扒”出来的。

现在回头看，这段经历刚好也是我从简单实用的 **Vibe Coding**，逐渐走向 **Engineering with AI** 的过程。

一开始，我想的是：

> 怎么让 AI 更快地把功能做出来？

后来我开始想：

> 怎么让 AI 不要把项目越做越乱？

再后来，问题变成了：

> 怎么建立一套工程系统，让人和不同的 AI Agent 都能在同一套规则里长期工作？

这三个问题看起来很接近，实际上对应的是完全不同的工程阶段。

---

## 01. 一切开始得非常 Vibe Coding

Gouno Blog 最初的开发方式，其实非常典型。

有一个想法，写提示词，创建项目，然后直接开始开发页面和功能。

缺什么补什么。

页面不好看，让 Agent 改。

这里差一个 Dialog，就做一个。

那里需要一个 Table，就加一个。

后台缺媒体管理，补。

评论管理还没做，再补。

一个 Agent 做完，下一个 Agent 继续接手。

在项目早期，这种方式真的很爽。

AI 把“从零到能用”的时间压缩得非常短。过去可能要先搭框架、定目录、选技术栈、讨论组件方案，再慢慢进入业务开发；Vibe Coding 的顺序几乎完全反过来了：

**先让它跑起来再说。**

而且在那个阶段，这并不一定是错的。

一个新项目最初最大的风险，往往不是代码不够漂亮，而是产品根本做不出来。所以当时我的优先级很直接：功能优先，先证明想法能跑，先把 Blog 做出来，先把 Admin 做出来。

真正的问题，是我低估了一件事：

### AI 写代码有多快，它制造技术债就可以有多快。

一个人长期维护一个项目，即使代码风格不够规范，至少通常还有自己的惯性。

但不同 Agent 不一样。

Agent A 喜欢这样封装。

Agent B 喜欢另一套命名。

Agent C 看到两段重复代码，顺手抽了一个组件。

Agent D 又觉得这个组件不够灵活，于是在外面再包一层。

Agent E 为了修一个页面，又给它增加一个新的 variant。

每一次修改单独看都可能说得通，甚至每一段代码拿出来都未必算“坏代码”。但当这种局部正确不断叠加以后，项目会出现一种很奇怪的状态：

**没有哪一处特别离谱，但整个项目越来越难理解。**

按钮长得差不多，却不是同一个 Button。

两个页面布局基本一样，实现方式却完全不同。

同一种 Card，有好几套 padding。

同一种操作，有的用 Dropdown，有的用 Popover，有的直接 absolute 定位。

有些页面直接堆 utility class，有些地方包了一层组件，有些组件外面又套了三层 wrapper。

每个 Agent 都在认真解决自己眼前的问题。

但没有人真正负责维护“整个系统应该是什么样”。

于是我第一次真正感受到一个 AI Coding 时代特别典型的问题：

> **局部正确，并不会自动累积成全局正确。**

![Vibe Coding 阶段：Agent 不断往项目里堆 UI 与代码](./assets/gouno-ui-vibe-to-engineering/02-vibe-coding-chaos.webp)

## 02. 功能稳定以后，我以为“规范化”只是一个清理工作

等 Gouno Blog 的主要功能逐渐稳定以后，我觉得终于可以开始收拾前端了。

于是我们开始做一些看起来非常正确的事情：

- 引入 Tailwind CSS，把样式逐渐收敛到统一体系；
- 引入 shadcn/ui、`cn`、`cva`、Radix UI 等基础能力；
- 统一 Button、Input、Dialog、Dropdown、Tabs 等组件；
- 让 Agent 做 UI/UX 走查、重复代码检查和 Design System Alignment；
- 使用能力越来越强的模型和 Agent，希望它们帮助完成更大范围的重构。

当时我的直觉是：

**底层工具这么成熟，模型也这么强，剩下的不就是让 AI 帮我整理一下吗？**

后来证明，这个想法太乐观了。

Tailwind 很好。

shadcn/ui 很好。

更强的 Agent 也确实能看更多文件、执行更多修改、跑更多测试。

但它们解决不了一个更根本的问题：

### 如果项目自己都不知道什么是“正确答案”，Agent 到底应该往哪里收敛？

比如项目里有三个类似的 Button。

Agent 应该把它们合并？

应该全部替换成统一组件？

应该给现有 Button 增加 variant？

还是三个场景的语义本来就不同，应该继续保持独立？

没有答案。

因为当时项目没有真正定义 Button 的公共 API 和职责边界。

再比如 Tabs。

TabBar 与 TabPanel 之间的距离谁负责？

TabPanel 应不应该给任意业务内容加 padding？

底部 indicator 是 Tabs 自己的视觉边界，还是允许溢出容器？

嵌套到左右布局以后，内容 gutter 又归谁管理？

如果这些问题没有统一答案，Agent 再聪明，也只能根据眼前代码猜。

这段时间我有一个很深的体会：Agent 可以非常勤奋。

不停扫描。

不停测试。

不停发现差异。

不停修改。

然后再次测试。

Token 消耗得很快，过程看起来也非常忙碌。

但过一段时间回头看，却会发现项目没有产生与这些 Token 消耗相匹配的结构性进步。

它很容易陷入这样的循环：

```text
发现局部问题
    ↓
修改局部问题
    ↓
引入新的局部差异
    ↓
继续扫描和测试
    ↓
再修改
```

甚至模型越强，这个问题有时候越明显。

弱一点的模型可能不敢大改。

强模型是真的“无所畏惧”。

如果方向没有定义好，它可以非常高效、非常自信地把一个错误方向实施得更加彻底。

![规范化阶段：大量组件、规则和测试在运转，但系统仍未真正收敛](./assets/gouno-ui-vibe-to-engineering/03-standardization-loop.webp)

## 03. 第一次真正的认知转折：问题不是 CSS，而是谁说了算

这时候我才慢慢意识到，我们真正缺的并不是一个更好的 CSS 方案，也不只是缺一个更好的组件库，更不是再换一个更强的模型。

真正缺的是：

**Source of Truth。**

到底谁来定义：

- Button 应该有什么能力？
- Tabs 的结构职责是什么？
- 页面容器负责什么？
- 组件负责什么？
- 哪些东西属于基础能力？
- 哪些属于复合 Pattern？
- 哪些才是 Gouno 产品族自己的结构和设计语言？
- 什么重复值得抽象？
- 什么重复应该暂时保留？
- 一个新的公共 API 凭什么可以进入设计系统？

这些事情如果都没有明确答案，那么 Agent 看到的只是“一堆代码”，而不是“一个系统”。

这两者的区别非常大。

于是我们开始把 UI 从具体产品里抽出来。

**Gouno UI 开始成为一个独立的问题。**

---

## 04. 第一次抽离 Gouno UI，我们又踩了另一个坑：太想照顾历史

刚开始抽的时候，我仍然背着 Gouno Blog 和 Admin 已有实现的包袱。

这个页面已经这么写了，最好兼容。

那个组件三个地方都用了，应该提出来。

某些 props 已经存在，尽量保留。

某些布局以后可能还会复用，提前封一下。

于是很自然地，我们开始尝试给 Gouno UI 划层级。

基础的放下面。

复用的放中间。

产品相关的放上面。

听起来没有问题。

但真正落地以后，层级非常乱。

有些组件说它是基础组件吧，里面又带着明显的业务语义。

说它是业务组件吧，几个页面又确实都在用。

放 Pattern 好像可以。

放 Gouno 好像也有理由。

再加上还要兼容已经开发出来的功能，边界开始越来越难解释。

这时我才意识到第二个很关键的问题：

> **“从现有代码里抽公共部分”和“设计一个正确的抽象体系”，其实是两件不同的事情。**

前者非常容易把历史偶然性包装成规范。

你会因为“以前就是这么写的”，把一些本来不应该进入设计系统的东西正式化。

某种意义上，这就像试图从一栋已经盖歪的房子里，总结出一套新的建筑规范。

![第一次分层：已经有了结构，但历史包袱让不同层之间充满交叉与牵连](./assets/gouno-ui-vibe-to-engineering/04-layered-abstraction.webp)

---

## 05. 最后我决定：先不要迁移历史，重新从地基开始

后来我做了一个现在看来非常重要的决定：

**先不要管 Blog 已经怎么写。**

**也先不要急着把 Admin 迁进来。**

先从最基础的问题重新开始：

一个现代 Web 产品真正高频使用的基础 UI 到底有哪些？

Button、Input、Select、Checkbox、Radio、Switch、Tabs、Card、Table、Dialog、Drawer、Dropdown、Tooltip、Popover、Badge、Toast……

先确定一个“够用”的基础集合。

然后不再凭感觉发明轮子，而是系统学习成熟设计系统是怎么处理这些问题的。

我们重点参考了 Ant Design、Ant Design Pro，同时结合 shadcn/ui 和 Radix 的组合方式。

这里所谓的“照搬”，真正值得复制的并不是颜色、圆角或者 CSS，更不是把源码机械复制一遍。

真正值得学习的是成熟系统经过大量实际使用验证之后形成的东西：

- 组件边界；
- API 语义；
- 状态模型；
- 组合方式；
- 可访问性职责；
- 哪些事情应该由组件负责，哪些应该交给调用方。

一个成熟组件库最有价值的地方，并不是告诉你 Button 应该长什么样。

而是它已经替整个生态反复回答过：

**什么东西值得成为一个 Button。**

于是 Gouno UI 的目标开始变得克制：

> 先把最常用、最稳定、最基础的能力做好。  
> 不急着创造高级抽象。  
> 不因为某个历史组件存在，就默认它有资格进入新的公共体系。  
> 先把地基做清楚。

---

## 06. Showcase 从“组件展览馆”变成了设计系统实验室

基础组件逐渐稳定以后，我们开始做 Showcase。

一开始它很像很多组件库都会有的 Demo：

展示 Button。

展示 Input。

展示 Table。

展示不同 size、variant 和状态。

但后来我越来越觉得，如果 Showcase 只展示孤立组件，它的价值非常有限。

因为真正难的从来不是“Button 单独看起来对不对”。

真正困难的是：

Button 放进 Table 以后对不对？

Table 放进 Tabs 以后对不对？

Tabs 放进完整 Admin Shell 以后对不对？

页面进入不同宽度以后对不对？

Loading、Empty、Error、Disabled、Destructive 等状态出现以后还对不对？

于是我们开始把真实产品页面放进 Showcase。

Gosso Admin。

Blog Admin。

Gouno Blog 的真实页面族。

真实页面不再只是“最终使用组件的地方”，而开始反过来成为设计系统的压力测试。

到今天，我认为 Showcase 至少有四个角色。

### 第一，它是组件说明书

组件有哪些公共 API，支持什么状态，怎么组合，边界在哪里。

### 第二，它是设计实验室

真正迁回产品之前，先在 Showcase 里解决布局、间距、阴影、层级、导航、Tabs、空状态、响应式行为等问题。

### 第三，它是集成验证场

单个组件正确不代表组合以后仍然正确。Showcase 用真实页面证明多个组件放在一起以后，设计语言、交互和布局仍然成立。

### 第四，它开始成为 AI 的可执行上下文

以前我们可能告诉 Agent：

> 把这个页面做得和其他页面一致。

这其实非常模糊。

后来可以告诉它：

> 使用当前 canonical Core / Theme / Gouno API，按照 Showcase 已验证页面的结构实现，并遵守仓库里的 Architecture、API Specification 和 Product-Driven Development 约束。

这已经不是同一个级别的指令了。

前者依赖模型“理解我的意思”。

后者依赖仓库里已经存在的事实。

我也越来越确信一件事：

> **好的 AI 工程，不应该依赖 AI 每一次都做出聪明判断，而应该尽量让正确答案已经存在于项目里。**

## 07. “三步法则”：第三次出现不是自动抽象，而是触发审查

做组件库很容易从“不抽象”走向另一个极端：过度抽象。

看到两个地方长得差不多，就抽组件。

再看到第三个地方类似，再加几个 props。

最后项目里充满：

`XXXWrapper`、`XXXContainer`、`XXXSection`、`XXXLayout`、`XXXManager`。

看起来代码复用了，实际上公共 API 越来越复杂，最后谁都不敢改。

所以后来我们把 **Rule of Three** 明确成了一个默认的发现规则：

1. **第一次出现：本地实现。** 不急着抽象。
2. **第二次出现：记录相似性。** 即使有少量重复，也允许继续本地实现，因为语义合同可能还没有稳定。
3. **第三次出现：停止继续复制，进入抽象审查。**

这里最重要的一点是：

### 第三次出现，也不等于“自动抽组件”。

三次语义等价的真实场景，只意味着我们终于有了足够证据，值得认真回答“它是否应该成为公共抽象”。

我们开始要求自己比较的也不只是 JSX 长得像不像，而是：

- 用户任务是否相同；
- 状态模型是否相同；
- 交互生命周期是否相同；
- Loading / Empty / Error / Disabled / Destructive 状态是否一致；
- 键盘、Focus、ARIA 行为是否一致；
- 响应式和布局约束是否一致；
- 数据槽位与 action policy 是否一致。

视觉一样，不一定是同一个组件。

文件名不一样，也不代表它们不是同一种 Pattern。

这让我慢慢接受了一件以前会觉得“不够优雅”的事情：

**重复代码不一定是坏代码。**

在真实合同还没有稳定之前，错误抽象往往比少量重复更贵。

## 08. 层级终于不是“目录分类”，而是依赖契约

在不断重做和真实页面验证以后，Gouno UI 的层级也逐渐稳定下来。

今天它的 canonical dependency direction 已经很清楚：

```text
components/primitives + lib
          ↓
        core
          ↓
        theme
          ↓
       patterns
          ↓
        gouno
```

而且这个结构最重要的并不是“有五个目录”。

重要的是：

**每一层到底拥有哪类问题，以及依赖只能朝哪个方向走。**

### Core：产品无关的 UI 能力

控件、布局、数据输入、导航、展示、反馈、Overlay 等基础能力。

### Theme：主题本身

主题状态、持久化和主题控制，不把它变成一个什么都往里塞的 Application Provider 层。

### Patterns：经过证据证明的复合交互

不是因为两个页面长得像就放进 Patterns，而是确实存在共享状态、行为、生命周期的复合交互以后才准入。

### Gouno：Gouno 产品族稳定共享的结构和展示策略

比如应用 Shell、PageContainer、PageHeader、Navigation 等产品族结构。

而旧时代抽出来、但还没有经过当前规则重新证明的东西怎么办？

我们后来甚至专门建立了 `src/legacy`。

Legacy 不是第五层。

它更像一个“历史博物馆”。

旧抽象可以作为 prior art 被查阅，但不能因为它以前存在，就重新自动获得 canonical 身份。

这个变化非常重要。

因为从这里开始，目录结构表达的不再只是“代码放在哪里”，而开始表达：

**我们对这个抽象到底有多大信心。**

![工程化阶段：基础组件、真实 Showcase、规则与反馈循环开始形成一个完整系统](./assets/gouno-ui-vibe-to-engineering/05-engineering-system.webp)

## 09. 设计规范不是先写完再执行，而是从真实问题里长出来

以前说到 Design System，我会天然想象一个流程：

先设计一份很完整的规范。

颜色是多少。

间距是多少。

阴影分几级。

圆角多少。

字号多少。

然后开发按照规范执行。

真正做 Gouno UI 以后，我发现实际过程往往更像：

```text
先实现
  ↓
放进真实场景比较
  ↓
发现不一致
  ↓
寻找不一致背后的共同规律
  ↓
把规律变成设计语言 / API / Architecture Rule
  ↓
测试和 Showcase 固化
  ↓
继续接受真实产品挑战
```

比如阴影。

开始可能只是觉得几个 Card 放在一起“不太统一”。

继续追以后才会遇到更多问题：普通 Surface 要不要阴影？Popover 和 Dialog 是不是同一级 elevation？Hover 能不能随便抬高？业务页面能不能自己再发明一套 shadow？

最后这些问题才会沉淀成 Surface / Elevation 的设计语言。

Tabs 也是一样。

一开始可能只是一个 Demo 里出现了滚动条。

继续追以后才会发现：indicator 应该留在组件自己的 visual / scroll boundary 内；Tabs 应该负责 TabBar 与 TabPanel 的结构关系，而任意业务内容的内部 padding 不应该由 TabPanel 擅自决定。

当你只修一个页面时，它是 Bug。

当你开始回答“以后所有同类组件应该怎样”时，它才开始变成设计系统。

所以我现在更愿意这样理解 Design System：

> **它不是一份预先写完的设计文档，而是大量真实产品决策经过验证后，被明确表达、测试并持续维护的一组合同。**

## 10. 从“一次性重构”到“阶段性收敛”

Gouno UI 另外一个很明显的变化，是开发节奏也变了。

以前很容易给 Agent 一个巨大目标：

> 把 UI 统一掉。

这个目标听起来明确，实际上几乎没有完成条件。

后来我们越来越习惯拆成一段一段：

这一阶段处理 Button。

下一阶段处理 Shadow / Elevation。

再处理 Tabs。

再处理 Shell。

再做 Gosso Admin 某一组真实页面。

再回头审查组件公共 API。

每完成一个阶段，就重新看源码、Showcase、真实场景和测试。

已经“完成”的组件也允许重新被挑战。

因为随着更多真实产品加入，昨天看起来合理的抽象，今天可能会暴露出过拟合。

这意味着工程化并不是追求“一次把架构设计正确”。

而是建立一个可以持续收敛的反馈循环。

---

## 11. Showcase 不是终点，真实产品必须反过来打脸设计系统

如果 Gouno UI 永远只活在 Showcase 里面，它最多只能算一个漂亮的 Demo。

所以后面我们开始把稳定的结果重新迁回真实产品，同时也把真实产品迁进 Showcase 作为 validation corpus。

这一步特别关键。

Showcase 里一个 API 看起来很优雅。

到了真实表单可能发现不够用。

Demo 里的 Table 很漂亮。

真实页面一加入批量操作、权限、Loading、Empty、Error 和响应式状态，问题马上就会出现。

所以后来我们的思路逐渐变成：

> **真实产品产生需求，Showcase 提供可重复验证，canonical UI 接受压力，最终再回到同一个真实场景验证。**

不是“先做一个万能组件库，再让所有产品服从它”。

而是 **Product-Driven Component Evolution**。

真实页面是需求来源。

设计系统是被真实需求不断证明出来的。

---

## 12. 再后来，我们甚至开始治理“一个 API 凭什么存在”

做到后面以后，讨论早就不只是“这个页面好不好看”。

问题开始变成：

一个公共属性应该叫什么？

同一种语义能不能存在两个写入入口？

历史 props 能不能因为兼容方便就继续留下？

一个组件的 owner 到底是 Core、Pattern、Gouno，还是应该留在 Product Local？

新增公共组件之前检查过哪些跨产品 prior art？

Showcase 里的重复能不能作为公共抽象证据？

于是项目里逐渐出现了：

- `docs/architecture.md`
- `docs/api-specification.md`
- `docs/product-driven-development.md`
- `docs/abstraction-register.md`
- `docs/api-conformance.md`
- `docs/design-language.md`

这时候我才发现，我们已经从“整理 UI”走到了另一个问题：

**这个系统怎样才能长期演化，而不是过几个月以后再次失控？**

这大概也是“写一个项目”和“治理一个工程”的区别。

---

## 13. 我后来真正踩过的坑，可以浓缩成几个判断

### 坑一：以为功能做出来以后，工程会自然变好

不会。

没有治理，项目只会继续积累熵。

### 坑二：以为换技术栈就等于解决架构问题

Tailwind 不是架构。

shadcn/ui 不是架构。

React 也不是架构。

它们都可以是很好的工具，但工具不会替项目定义职责边界。

### 坑三：以为更强的 AI 可以替代规范

我现在反而越来越相信：

**模型能力越强，规范越重要。**

因为强 Agent 执行得更快、修改范围更大、重构更大胆。

如果方向错了，它也只会更高效地制造错误。

### 坑四：过早抽象

第一次重复就抽。

需求还没稳定就抽。

最后抽出来的往往不是公共能力，而是历史偶然。

### 坑五：只做组件，不做真实使用场景

Button Demo 再完整，也证明不了完整产品。

设计系统真正困难的地方发生在组件之间的组合关系里。

### 坑六：把聊天上下文当成工程记忆

这一点是 AI 项目尤其容易犯的错误。

一次 Chat 里把背景解释得再完整，下一个 Agent、下一个 Session 也未必拥有同样的上下文。

如果一个关键决策只存在聊天记录里，它实际上就还没有真正进入工程。

---

## 14. 从 Vibe Coding 到工程化，我最大的成长其实不是“更会写前端了”

如果让我总结这段经历，我不会把最大的收获概括成：

我学会了 Tailwind。

我学会了 shadcn/ui。

我学会了怎么封装组件库。

这些当然都重要。

但真正发生变化的是，我开始越来越关注以前很少主动追问的问题：

什么是系统边界？

谁是 Source of Truth？

一个抽象存在的证据是什么？

什么东西应该标准化？

什么东西应该允许自由？

一个 API 为什么应该公开？

怎样证明设计已经稳定？

怎样让不同的人、不同模型、不同 Agent，在几个月之后仍然沿着同一个方向修改项目？

从这个角度看，所谓工程能力，很大一部分其实是在学习：

**如何控制一个软件系统的熵。**

---

## 15. AI 越强，我反而越觉得我们需要工程

Vibe Coding 给人的第一感觉，很容易是：

以后代码都可以生成了，是不是越来越不需要这些工程规范了？

但我这一轮做下来，越来越觉得结论可能恰恰相反。

过去一个程序员一天能写多少代码是有限的。

项目就算乱，熵增加的速度也有限。

现在几个 Agent 可以同时分析、修改几十个文件。

代码生产能力突然放大以后，如果没有清晰的 Architecture、稳定的公共 API、可执行的 Showcase、统一的设计语言、测试约束、阶段性 Review 和抽象准入机制，那么 AI 带来的就不仅仅是生产力。

还有：

**前所未有的技术债生产速度。**

所以我现在越来越觉得，AI Coding 进入下一个阶段以后，开发者真正重要的能力可能不只是“会不会写 Prompt”。

也不只是能不能让 Agent 一口气完成更多任务。

更重要的是：

> **设计规则、建立边界、构造反馈系统，然后让很多 Agent 在这个系统里长期稳定协作。**

---

## 16. 一个很有意思的终点：不要让下一个 Agent 再来问我当时是怎么想的

Gouno UI 目前有一条我非常喜欢的 Agent / Session Handoff 规则。

新的 Agent 如果要参与产品迁移、组件抽象或者公共 API 演化，需要先读仓库里的 Architecture、API Specification、Product-Driven Development、Abstraction Register 等约束。

其中有一句话几乎可以概括我这一路最大的认知变化：

> **不要从聊天历史里重新推测开发哲学，仓库文档才是持久的 Source of Truth。**

这句话如果放在几个月以前，我可能不会觉得它有什么特别。

现在却觉得，它几乎就是整个 Gouno UI 迭代过程的答案。

最早的时候，是我不停通过 Prompt 告诉 Agent：

“这个应该这样。”

“那个不要那样。”

“这里和之前保持一致。”

“记得我们刚才说过的规则。”

而工程化真正开始以后，目标变成了：

**我不应该需要每次重新解释。**

正确的边界应该存在于目录里。

正确的 API 应该存在于类型里。

正确的设计应该存在于 Showcase 里。

正确的决策应该存在于文档里。

不允许发生的事情应该由测试拦住。

Agent 换了没有关系。

Session 断了也没有关系。

因为工程本身记得。

---

## 写在最后

Gouno UI 当然还没有“完成”。

实际上，一个真正长期使用的 Design System 可能永远也没有彻底完成的那一天。

组件会继续被挑战。

Patterns 会继续被证明或者被否定。

新的真实产品还会暴露新的问题。

今天认为正确的 API，未来也可能被更充分的证据推翻。

但和最开始相比，我现在反而没有那么焦虑“什么时候全部做完”。

因为最大的变化不是：

**终于把 UI 做好了。**

而是：

**终于逐渐建立了一套知道应该怎样把它做好的方法。**

从：

```text
让 AI 把页面写出来
```

到：

```text
让 AI 使用统一组件写页面
```

再到：

```text
让 AI 在 Architecture、API、Design Language、Showcase、
Product Evidence 和 Tests 共同组成的工程约束里工作
```

看起来只是多了一堆目录、规范和测试。

实际上背后是完全不同的软件开发方式。

如果一定要给这一段经历取一个名字，我想大概就是：

# 从 Vibe Coding，到 Engineering with AI。

Vibe Coding 让我第一次强烈感受到：

**一个人可以做以前一个团队才能做出来的东西。**

而工程化又让我重新认识到：

当一个人真的拥有了一支 AI 团队以后，最重要的能力已经不再只是：

**自己能写多少代码。**

而是：

**你能不能让整个团队，长期写出同一个系统。**

这可能才是 AI 编程真正进入工程时代以后，我们需要重新学习的东西。
